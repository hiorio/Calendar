# UI 디자인 결정 사항

의뢰서("공유 캘린더 앱 UI 디자인 의뢰서", 2026-07-26)에 대한 시안 작업의 결과입니다.

> **현재 상태 — 2026-07-27 코드 반영 완료.**
> `src/constants/theme.ts`에 살구 light/dark 토큰과 크롬 토큰을, 캘린더 색에는 아래 순서의
> 12색 배경·글자 쌍을 적용했습니다. 아래 5장은 구현의 기준이자 변경 시 확인할 표입니다.

시안 파일: **`docs/design/ui-proposal.html`** — 브라우저로 열면 됩니다. 외부 의존이 없는
단일 파일이고, 상단에서 세 방향과 앱 다크모드를 실시간으로 전환할 수 있습니다.

## 1. 확정된 것

### 기본 테마 — 살구

세 방향(살구 · 쪽빛 · 먹빛)을 만들어 **살구를 기본으로 확정**했습니다. 앱 아이콘 ·
스플래시 · 스토어 스크린샷 · 첫 실행이 이 색을 씁니다.

셋 다 TimeTree의 시그니처 초록을 피했고 서로 다른 색상환 구역에 있습니다.

### 사용자 테마 — 세 방향을 모두 제공

살구를 브랜드 기본값으로 유지하면서 쪽빛과 먹빛도 설정에서 선택할 수 있게 확정했습니다.
테마는 계정이 아니라 **이 기기의 보기 설정**이며, 각 테마는 시스템 라이트/다크 모드에
맞는 두 색 토큰을 갖습니다. 캘린더 라벨 12색은 테마와 무관하게 유지합니다.

### 간격 · 라운드 · 타이포는 바꾸지 않는다

현재 `theme.ts`의 값이 요구사항(4pt 그리드)을 이미 충족합니다. 시안도 그 값 위에
그렸습니다. **바뀌는 것은 색 토큰뿐입니다.** 타이포만 6→8단계로 늘립니다(`11`, `34` 추가).

### 캘린더 라벨은 12색이고, 순서가 규칙이다

색상환을 고르게 도는 것만으로는 색약 대응이 안 됩니다. 사람이 안정적으로 가려내는 회색
단계는 예닐곱 개뿐이라 12색을 전부 서로 구분시키는 것은 **불가능합니다.**

그래서 색상이 아니라 **순서**를 설계했습니다 — 명도가 어둡게·밝게 번갈아 가도록 배열해서,
캘린더를 만들 때 팔레트 순서대로 배정하면 **인접한 두 캘린더는 흑백에서도 갈립니다.**

**팔레트 순서를 바꾸지 마세요.** 순서가 곧 규칙입니다.

### 캘린더 색과 개인 색의 우선순위

| 화면 | 색면 | 왼쪽 띠 |
|---|---|---|
| 홈 월간 뷰 (여러 캘린더가 겹침) | 캘린더 색 | 개인 색 |
| 개별 캘린더 홈 (캘린더 고정) | 개인 색 | 없음 |
| 하단 시트 · 상세 | 캘린더 색 (4px 세로 막대) | 개인은 아바타로 |

홈에서 사용자가 더 자주 던지는 질문은 "누구 일정이지?"가 아니라 "어느 캘린더지?"입니다.
자주 묻는 쪽에 넓은 면적을 줍니다.

> **1차 출시 권고 — 개인 색을 아예 쓰지 않기.** 라벨 12색에 개인 색까지 겹치면 한 화면에
> 색이 20개 넘게 등장합니다. 개인 구분은 아바타로 충분합니다.

### 온보딩 흐름을 의뢰서와 다르게 간다

의뢰서 3.A는 스플래시 → 로그인 → 가입 → 프로필 → 첫 진입 순입니다. 그런데 이 앱은
**가입을 앞세우지 않습니다**(`AGENTS.md` 제품 원칙, 이미 그렇게 구현돼 있음).

- 스플래시 → **첫 진입(게스트로 바로 시작)** → 캘린더 만들기 / 초대 링크로 참여
- 로그인·가입은 **공유하려 할 때 만나는 화면**
- A-3(이메일 가입/로그인)은 별도 화면이 아니라 A-2 안의 전환 탭 — 입력 필드가 거의 같습니다

"3분 안에 첫 일정 등록"이라는 목표에 가입 폼이 그 3분의 대부분을 먹기 때문입니다.

## 3. 시안에서 발견해 고친 것

되풀이하지 않도록 남깁니다. 셋 다 시안을 브라우저에서 실제로 렌더해 보고 찾았습니다.

**살구의 primary와 danger가 색상각 13도 차이였습니다.** 주황 브랜드(`#E2673F`, 15°)에
danger를 그냥 빨강(`#D13A34`, 2°)으로 두니, 하필 반복 수정 범위 시트(D-3)가 파괴적 경고와
확인 버튼을 한 화면에 놓는데 구분이 약했습니다. 적녹색약에서는 사실상 같은 색입니다.
`#B01B3F`로 색상각을 벌렸습니다. **주황 계열 브랜드에서는 danger를 빨강으로 두면 안 됩니다.**

**라벨은 배경 하나가 아니라 배경·글자 한 쌍입니다.** 명도를 번갈아 두면 밝은 라벨 위의 흰
글씨가 읽히지 않습니다. 슬롯마다 전경색을 함께 정의했습니다.

**커버 사진이 없을 때 흰 제목의 대비가 1.06이었습니다.** 기본 커버를 연한 크림으로 두고 그
위에 흰 글자를 얹었더니 사실상 안 보였습니다. 기본 커버를 브랜드 색 그라디언트로 채우고
스크림을 강화해 12.8~15.9로 올렸습니다.

아니라 데이터를 구분하는 부호라서, 테마를 바꿨다고 "가족은 파랑"이 달라지면 색으로 구분하던

표의 값이 각 색에 맞춰 조정된 것이라 더 낫습니다. 명시 방식으로 가면 `onColor`는 사용자가
직접 고른 임의 색에만 남겨 두세요.

## 7. 이름과 마크 — TimeLine

서비스명은 **TimeLine**입니다.

### 마크

**가로 막대 세 개가 시작점을 어긋내며 쌓인 모습**입니다. 두 가지를 동시에 말합니다.

- 이름이 말하는 **시간의 흐름** — 시작 위치가 한 칸씩 밀려 대각선을 만듭니다.
  셋 다 왼쪽에 붙이고 길이만 다르게 하면 햄버거 메뉴로 읽힙니다. 그래서 어긋냅니다.
- **여러 사람의 일정이 겹치는 것** — 투명도가 1.0 · 0.74 · 0.48로 내려갑니다.

이 앱의 월간 뷰에서 하루 칸에 일정이 색 막대로 쌓이는 모습을 그대로 가져왔습니다.
제품이 실제로 보여 주는 것이 곧 마크입니다.

바탕은 확정 브랜드색인 살구 그라디언트(`#E8734C` → `#C9552F`)입니다.

### 아이콘 생성

`npm run icons` (= `node scripts/make-icons.mjs`)가 전부 만듭니다. 외부 라이브러리를
쓰지 않습니다 — 도형이 둥근 사각형뿐이라 부호거리로 안티에일리어싱을 직접 계산하고,
PNG 인코딩은 Node 내장 zlib로 끝납니다. **PNG를 손으로 고치지 말고 스크립트를
고친 뒤 다시 돌리세요.**

| 파일 | 크기 | 용도 |
|---|---|---|
| `icon.png` | 1024 | iOS·스토어. 바탕까지 채움 |
| `android-icon-background.png` | 1024 | Adaptive 배경(단색) |
| `android-icon-foreground.png` | 1024 | Adaptive 전경. 바깥 33%가 잘리므로 마크를 좁게 |
| `android-icon-monochrome.png` | 1024 | Android 13+ 테마 아이콘 |
| `splash-icon.png` | 512 | 스플래시. 배경색은 `app.json`이 칠함 |
| `favicon.png` | 96 | 웹 |

### 이름이 들어가는 곳 / 안 들어가는 곳

**들어갑니다** — 앱 아이콘 이름, 스플래시, 온보딩, 스토어. 즉 *아직 이 앱을 모르는
사람에게 정체를 알리는 자리*입니다.

**안 들어갑니다** — **홈 화면.** 캘린더 앱을 연 사람은 자기가 뭘 열었는지 압니다.
화면에서 가장 값진 자리를 이름에 쓰면 그만큼 격자가 줄어듭니다. 그 자리에는 지금
보고 있는 **달**을 둡니다. 월간 뷰 안에 있던 중복 제목은 없앴습니다.

### 스킴과 식별자

앱 스킴은 환경을 섞지 않도록 `timeline-development://`, `timeline-preview://`,
`timeline://`로 나눴습니다. `Linking.createURL`과 `makeRedirectUri`는
`app.config.ts`에서 파생됩니다. 클라우드 Supabase에는 사용하는 환경의
`<scheme>://auth-callback`을 각각 등록합니다.

iOS 번들 식별자는 저장소에 `com.example.*` 자리표시자를 두지 않습니다.
EAS 환경의 `APP_IOS_BUNDLE_IDENTIFIER`에서 조직이 소유한 실제 식별자를 받고,
`npm run deploy:check`가 누락과 예시 값을 배포 전에 차단합니다.
