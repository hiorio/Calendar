# 설계안 대비 변경점

설계안(공유 캘린더 앱 상세 설계안)을 구현하면서 **바꾼 것**과 **왜 바꿨는지**를 모아둡니다.
설계 문서 자체는 그대로 두고, 실제 스키마와의 차이를 여기서 추적합니다.

---

## 1. `events.range_start` / `range_end` 추가 (중요)

**문제.** 설계안 6.1의 기간 조회 조건은 `start_at`을 기준으로 합니다.

```sql
(rrule is null and start_at < :to and end_at > :from)
or
(rrule is not null and start_at < :to and (rrule_until is null or rrule_until > :from))
```

그런데 3장 원칙에 따라 **종일 일정은 `start_at`이 NULL**입니다(`start_date`만 씀).
즉 위 조건으로는 종일 일정이 한 건도 잡히지 않습니다. "매년 5월 3일 생일" 같은
종일 + 반복 조합은 흔하기 때문에 이건 그냥 버그가 됩니다.

**해결.** 조회/인덱스 전용 파생 컬럼 두 개를 트리거(`sync_event_range`)로 유지합니다.

| 컬럼 | 값 |
|---|---|
| `range_start` | 시간 지정이면 `start_at`, 종일이면 `start_date`를 `events.timezone`으로 환산한 시각 |
| `range_end` | 단일 일정이면 종료 시각(종일은 마지막 날 +1일 00:00, **배타적**), 반복이면 `rrule_until`. NULL이면 무한 반복 |

`start_at` / `start_date`는 설계안 그대로 유지합니다. 파생 컬럼은 **직접 쓰지 않습니다.**

**바뀐 조회 조건:**

```sql
select * from events
where calendar_id in (:calendar_ids)
  and deleted_at is null
  and range_start < :to
  and (range_end is null or range_end > :from);
```

단일/반복/종일이 한 조건으로 처리되고 `idx_events_calendar_range`를 그대로 탑니다.

## 2. `rrule_until`의 의미를 고정

설계안은 "UNTIL 값 복제"라고만 되어 있는데, `COUNT=10` 처럼 UNTIL이 없는 규칙에서는
복제할 값이 없습니다. 그대로 두면 유한 반복이 무한으로 취급됩니다.

**규칙:** `rrule_until`에는 **마지막 회차의 종료 시각**을 넣습니다.

- `UNTIL`이 있으면 그 회차의 종료 시각
- `COUNT`가 있으면 전개해서 마지막 회차의 종료 시각
- 둘 다 없으면 NULL (무한)

4단계에서 만들 RRULE 순수 함수 모듈이 이 값을 계산해 저장합니다.

## 3. `event_exceptions` 보강

- `start_date` / `end_date` 오버라이드 컬럼 추가 — 종일 반복 일정의 한 회차만 수정하는 경우
- `created_at` / `updated_at` 추가 — 오프라인 큐 충돌 판정(7.3)에 필요
- `original_start` 규약 명시: **종일 반복 일정은 해당 날짜 00:00을 `events.timezone`으로
  환산한 값**을 씁니다. 클라이언트와 서버(`reminder/scan`)가 같은 규약을 써야 합니다.

## 4. 무결성 제약 보강

| 대상 | 내용 |
|---|---|
| `events` CHECK | 시간 컬럼과 날짜 컬럼이 **상호 배타**임을 강제. `end_at > start_at`, `end_date >= start_date` |
| `attachments` | `memo_id` FK 누락 보완, `event_id`/`comment_id`/`memo_id` 중 **정확히 하나**만 채우도록 CHECK, `storage_path` UNIQUE |

| `device_tokens` | `disabled_at` 추가 — 12장의 stale token 정리용 |
| `notification_outbox` | `attempts`, `last_error` 추가 — 8.2의 "최대 3회 재시도"를 기록할 자리가 없었음 |

## 5. 구성원 규칙을 정책이 아니라 트리거로

RLS 정책만으로는 "본인이 자기 role을 OWNER로 올리는 것"이나 "OWNER가 소유권을 넘기지 않고
탈퇴하는 것"을 막을 수 없습니다(정책은 행 접근 여부만 판단하고 값 변화는 못 봅니다).
`20260726000200_membership_rules.sql`의 트리거가 담당합니다.

- 소유권 이전은 현 OWNER만, 새 소유자는 구성원이어야 함, `calendar_members.role`도 함께 이동
- 역할 변경은 OWNER만
- OWNER는 다른 구성원이 있으면 탈퇴 불가
- 마지막 1인이 나가면 캘린더 soft delete

`auth.uid()`가 NULL인 경우(= service_role로 도는 Edge Function)는 통과시킵니다.
서버 로직이 자체 검증합니다.

## 6. `calendar_members`에 클라이언트 INSERT 정책 없음

가입은 초대 코드 검증을 거쳐야 하는데, 비구성원은 `calendar_invites`를 읽을 수 없습니다
(읽을 수 있게 하면 코드 목록이 새어 나갑니다). 따라서 **합류는 반드시 `invite/accept`
Edge Function(service_role)을 통해서만** 일어납니다. 2단계 구현 시 전제입니다.

같은 이유로 `profiles` 조회는 "나 자신 + 같은 캘린더 구성원"으로 제한했습니다.
초대 링크 미리보기에서 캘린더 이름·구성원을 보여주려면 그것도 Edge Function이 내려줘야 합니다.

## 7. Storage

- `calendar-media` (비공개): 경로 `{calendar_id}/{uuid}.{ext}`, 첫 세그먼트로 구성원 검사
- `avatars` (공개 읽기): 경로 `{user_id}/{uuid}.{ext}`

설계안에 없던 `avatars`를 추가했습니다. `profiles.avatar_url`이 채워지려면 어딘가에는
올려야 합니다.

## 8. RLS만으로는 부족하다 — GRANT가 먼저다 (실행하며 발견)

`authenticated`에게 테이블 권한을 주지 않아 **모든 요청이 42501로 막혔습니다.**
RLS는 GRANT 위에 얹히는 필터라, GRANT가 없으면 정책이 무엇이든 통과하지 못합니다.

Supabase의 `public` 스키마 기본 권한은 `authenticated`에게 `Dxtm`(TRUNCATE, REFERENCES,
TRIGGER, MAINTAIN)만 주고 SELECT/INSERT/UPDATE/DELETE는 주지 않습니다. `service_role`도
같은 상태여서 Edge Function도 전부 막힙니다.

`20260726000500_grants.sql`에서 명시적으로 부여합니다. 부여 목록은 0003의 정책 목록과
1:1로 맞췄습니다. **새 테이블을 추가하면 이 파일도 함께 갱신해야 합니다.**

## 9. 캘린더 생성 시 RETURNING이 막히던 문제 (실행하며 발견)

`calendars`에 INSERT하면 `new row violates row-level security policy`가 났습니다.
RETURNING 없이 INSERT하면 성공하는 것으로 원인이 확인됐습니다.

PostgREST는 삽입 결과를 돌려주려고 항상 RETURNING을 붙이고(= supabase-js의
`.insert().select()`), PostgreSQL은 RETURNING 행에 SELECT 정책을 적용합니다. 그런데
OWNER 구성원 행을 만드는 `on_calendar_created`는 **AFTER INSERT** 트리거라 그 시점엔
아직 실행되지 않았고, 따라서 `is_calendar_member(id)`가 false였습니다.

`20260726000600_fix_calendar_insert_returning.sql`에서 SELECT 정책에
`owner_id = auth.uid()`를 더했습니다. 의미상으로도 소유자는 구성원 행과 무관하게 자기
캘린더를 봐야 하고, 소유권 이전 시 `owner_id`가 함께 바뀌므로 권한이 남지 않습니다.

> 교훈: "행을 만든 뒤에야 볼 수 있게 되는" 정책은 INSERT ... RETURNING과 충돌합니다.
> 앞으로 정책을 쓸 때 삽입 직후의 가시성을 항상 같이 확인할 것.

## 10. 가입을 시작 조건에서 뺐다 (설계안 10장 변경)

설계안 1차 범위는 "회원가입/로그인"이 첫 관문이었습니다. 앱을 처음 켠 사람에게 가입부터
요구하면 이탈이 큽니다. 캘린더에 일정 하나 적어보는 것까지는 계정이 없어도 됩니다.

**바꾼 것:** Supabase 익명 로그인으로 게스트 세션을 발급해 바로 시작합니다.
가입은 계정이 실제로 필요해지는 순간(공유)에만 요구합니다.

- 첫 실행 → `signInAnonymously()`. 로그인 화면을 거치지 않습니다.
- 게스트도 캘린더·일정·메모를 만들 수 있습니다. 스키마와 RLS는 그대로입니다.
  익명 사용자도 JWT의 `role`은 `authenticated`이기 때문입니다.
- 가입은 `/account` **모달**입니다. 설정 탭이나 게이트에 걸린 기능에서 엽니다.
- 게스트 → 계정은 `updateUser({ email, password })`로 **연결**합니다. `user.id`가 그대로라
  지금까지 쓴 데이터가 유지됩니다. 소셜은 `linkIdentity()`.
- 이미 있는 계정으로 **로그인**하면 게스트 기록은 따라오지 않습니다. 화면에서 경고합니다.

### 어디서 가입을 요구하는가

"공유"가 경계입니다. 초대 링크 발급에 계정을 요구하고, 이걸 **RLS로 강제**합니다
(`0007_guest_first.sql`). UI에서만 막으면 anon key로 우회됩니다.

```sql
create policy "invites: signed-up member can create" on public.calendar_invites
  for insert to authenticated
  with check (... and not public.is_guest());
```

`is_guest()`는 JWT의 `is_anonymous` 클레임을 봅니다.

### 함정: 계정이 돼도 토큰은 한동안 게스트다

`updateUser()`로 계정을 만들어도 **들고 있던 access token의 `is_anonymous`는 여전히
true**입니다. 갱신될 때까지(기본 1시간) `is_guest()`가 true라 공유가 계속 막힙니다.
`createAccount()`에서 `refreshSession()`을 명시적으로 호출합니다.
(`npm run db:smoke`의 12번 항목이 이 동작을 고정합니다.)

### 빈 게스트 계정 정리

서버가 진짜 계정 행을 발급하는 방식(Supabase 익명 로그인, Firebase Anonymous Auth)에서는
설치·재설치·스토리지 삭제·봇 요청마다 계정이 하나씩 남습니다. 두 곳 다 주기적 정리를
권고하는 표준 관리 항목입니다.

우리 스키마에서는 이게 자연히 안전합니다. `calendars.owner_id → profiles(id)`에 cascade가
없어서 **데이터를 가진 게스트는 FK가 삭제를 막습니다.** 즉 아래 배치가 지울 수 있는 건
아무것도 만들지 않은 빈 계정뿐입니다.

```sql
-- pg_cron으로 하루 1회. 필요해지면 마이그레이션으로 추가한다.
delete from auth.users
 where is_anonymous
   and created_at < now() - interval '30 days';
```

지금 넣지 않은 이유: 아직 사용자가 없어 정리할 것도 없고, 보관 기간(30일이 맞는지)은
실제 사용 패턴을 보고 정해야 합니다.

**미해결:** 캘린더를 만들고 방치한 게스트의 데이터는 영구 보존됩니다. 이건 기술이 아니라
보관 정책 결정입니다.

### 남은 것

- 게스트 상태로 앱을 지우면 데이터가 사라집니다. 화면에서 고지합니다.
- 2차: 이미 계정이 있는 사람이 게스트로 쓰던 내용을 **병합**하는 흐름.
  지금은 병합하지 않고 경고만 합니다.

## 11. 홈 탭을 없앴다 (설계안 9장 변경)

설계안 하단 탭은 홈(통합 뷰) · 캘린더(목록/개별) · ＋ · 활동 · 설정 다섯 개였습니다.
그런데 홈과 캘린더가 결국 같은 월간 뷰였습니다. 캘린더 앱의 첫 화면은 캘린더여야 합니다.

- 탭은 넷: **캘린더 · 추가 · 활동 · 설정**
- 앱을 켜면 곧바로 월간 뷰
- 여러 캘린더는 상단 **필터 칩**으로 켜고 끕니다 (설계안 홈의 칩을 그대로 가져옴).
  선택 상태는 Zustand + AsyncStorage에 남습니다.
- 캘린더 **목록·관리**는 탭이 아니라 칩 줄 끝의 "관리"에서 여는 화면으로 내렸습니다.

## 12. 초대 수락을 Edge Function 대신 SQL 함수로 (설계안 6.2 변경)

설계안은 `POST /invite/accept`를 Edge Function으로 뒀습니다. 그런데 하는 일이
"코드 검증 → 멤버 등록 → use_count 증가 → 활동로그"로 **전부 DB 안에서 끝납니다.**

`security definer` 함수로 만들면:

- 한 트랜잭션으로 묶입니다. `for update`로 코드 행을 잠가 동시 수락 시 use_count가
  어긋나지 않습니다.
- 콜드스타트가 없고, 배포 단계도 사라집니다.
- 로컬에서 `npm run db:smoke`로 바로 검증됩니다.

`public.accept_invite(text)`와 미리보기용 `public.invite_preview(text)` 두 개입니다.
비구성원은 `calendar_invites`를 읽을 수 없으므로(코드 목록이 새면 안 되므로) 조회도 이
함수를 통해서만 합니다. 외부 호출이 필요해지면 그때 Edge Function으로 옮깁니다.

수락에도 계정을 요구합니다. 공유 캘린더는 기기를 바꿔도 이어져야 하는데 게스트는 그럴
수 없기 때문입니다.

## 13. 소유권 이전이 자기 가드에 걸리던 버그 (실행하며 발견)

`OWNER는 소유권을 넘길 수 있다` 검사가 403으로 실패했습니다.

`guard_calendar_owner_change`는 `calendar_members`를 두 번 고칩니다 — 현 소유자를
MEMBER로 강등하고, 새 소유자를 OWNER로 승격합니다. 그런데 첫 번째 update가 **호출자
자신을 강등**해 버리고, 두 번째 update에서 `guard_member_role_change`가
"auth.uid()가 calendar_members에서 OWNER인가"를 확인하며 막았습니다. 순서를 바꿔도
두 번째에서 같은 문제가 납니다.

`0009`에서 역할 변경 권한의 기준을 `calendar_members.role`이 아니라 **`calendars.owner_id`**로
바꿨습니다. 소유자의 단일 출처는 원래 이쪽이고, BEFORE UPDATE 시점에는 아직 예전 소유자가
들어 있어 두 update가 모두 통과합니다. 일반 구성원이 스스로 OWNER가 되는 것은 그대로
막힙니다(`npm run db:smoke` 13번이 두 경우를 다 고정합니다).

## 14. 웹에서는 날짜 선택기를 갈랐다 (3단계)

Expo가 안내하는 `@react-native-community/datetimepicker`는 **Android·iOS만 지원합니다.**
그런데 이 프로젝트의 확인 경로는 웹 미리보기입니다. 웹에서 날짜 입력이 통째로 비면
개발 중에 일정 기능을 손댈 수가 없습니다.

`src/components/ui/date-time-field.tsx` / `.web.tsx`로 갈랐습니다. 이미 저장소에 있던
`use-color-scheme.web.ts`와 같은 방식입니다.

- 네이티브: 시스템 선택기 (iOS는 compact 위젯, Android는 눌러서 다이얼로그)
- 웹: `input[type=date]` / `input[type=time]`. 브라우저가 이미 좋은 선택기를 갖고 있어서
  흉내 낼 이유가 없습니다. `colorScheme`을 넘겨 달력 팝업까지 같은 배색을 씁니다.

화면 쪽 코드는 어느 플랫폼인지 모릅니다. `DateTimeField` 하나만 씁니다.

## 15. 종일 ↔ 시간 지정 전환은 값까지 바꾼다 (3단계)

`events_time_shape` 검사 때문에 토글만 뒤집으면 저장이 400으로 실패합니다. 종일은
`start_date`/`end_date`만, 시간 지정은 `start_at`/`end_at`만 있어야 합니다.

`lib/event-time.ts`의 `switchAllDay`가 전환하는 순간 값을 그 모양으로 맞춥니다.
같은 이유로 `moveStart`는 시작을 옮길 때 종료를 같은 간격으로 끌고 가고, `moveEnd`는
종료가 시작보다 앞서면 밀어 줍니다. **에러를 보여 주고 고치게 하는 대신 애초에 그
상태를 만들지 않습니다.**

## 16-a. 반복 전개는 벽시계 공간에서 한다 (4단계)

**"매주 화요일 9시"는 서머타임이 바뀌어도 9시입니다.** 회차를 UTC 순간으로 세면
3월에 한 시간이 밀려 8시나 10시가 됩니다.

rrule에 tzid를 맡기려면 luxon이 필요합니다. 그 하나 때문에 의존성을 더하는 대신
`Intl`이 이미 갖고 있는 tz 데이터를 씁니다(`src/lib/timezone.ts`).

1. 시작 시각을 `events.timezone`의 **벽시계**로 읽는다
2. 그 벽시계를 "UTC인 척하는" Date로 만들어 rrule에 넘긴다 (회차 세기)
3. 각 회차를 다시 `events.timezone`의 벽시계로 보고 실제 순간으로 되돌린다

오프셋을 알려면 순간이 필요하고 순간을 알려면 오프셋이 필요해서, 한 번 추정하고
그 값의 오프셋으로 한 번 더 보정합니다(`fromWallClock`). 서머타임 경계는
`npm run test:unit`이 뉴욕 기준으로 고정합니다.

종일 반복은 날짜만 옮깁니다. 3장 원칙대로 타임존 변환 대상이 아닙니다.

## 16-b. `rrule_until`은 클라이언트가 채운다 (4단계)

`range_end`는 트리거가 유지하지만, 반복 일정일 때 그 값은 `rrule_until`을 그대로
가져옵니다(1번 항목). 그런데 **RRULE의 UNTIL/COUNT를 실제 마지막 회차의 종료
시각으로 푸는 일은 SQL에서 하기 나쁩니다.** Postgres에 RRULE 파서가 없습니다.

`computeRruleUntil`이 저장 직전에 계산해 함께 보냅니다. 이 값이 틀리면 끝난 반복
일정이 계속 조회되거나 살아 있는 일정이 사라지므로, 화면이 아니라 쿼리 계층
(`features/events/queries.ts`)에서 항상 덧붙입니다.

## 16-c. 순수 함수 테스트를 붙였다 (4단계)

반복 전개와 타임존 변환은 DB도 화면도 거치지 않는 계산이라 스모크 테스트로
드러나지 않고, 서머타임 경계는 브라우저로 확인하기 어렵습니다.

`npm run test:unit` — Node 24가 TypeScript를 스스로 벗겨내므로 빌드 단계 없이
`src/lib/*.ts`를 직접 부릅니다. Metro와 Node의 모듈 해석 차이(확장자 없는 import,
`@/` 별칭, rrule의 CJS 진입점)만 `scripts/ts-resolve.mjs`가 메웁니다.

## 16-d. "이후 모두 수정"은 넣지 않았다 (4단계)

삭제는 세 범위를 다 지원합니다 — 이 회차만(`CANCELLED` 예외), 이후 모두(마스터의
UNTIL을 직전으로 당김), 전체(soft delete).

수정은 **이 회차만**(`MODIFIED` 예외)과 **전체**만 됩니다. "이후 모두 수정"은
시리즈를 두 개의 events 행으로 쪼개고 기존 예외를 나눠 옮겨야 해서, 규모가 나머지
셋을 합친 것과 비슷합니다. 화면에서 그 범위를 고르면 왜 안 되는지 알리고 삭제만
열어 둡니다. 반쯤 동작하는 것보다 없는 편이 낫습니다.

## 16-e. 참여자·댓글은 회차가 아니라 일정에 붙는다 (5단계)

스키마가 `event_participants(event_id, user_id)`, `event_comments(event_id, …)`라
**회차를 구분하지 않습니다.** 반복 일정이라면 3월 회차에 남긴 댓글이 4월 회차에도
보입니다.

바꾸지 않았습니다. 대부분의 경우 "이 모임"에 대한 대화지 "3월 12일의 그 모임"에
대한 대화가 아니고, 회차별로 나누려면 `event_exceptions`처럼 회차 키를 하나 더
들고 다녀야 합니다. 대신 **화면에서 그 사실을 알립니다** — 반복 일정의 댓글창 위에
"모든 회차가 함께 봅니다"를 띄웁니다. 모르고 쓰는 것이 문제지, 공유되는 것 자체는
문제가 아닙니다.

## 16-f. `event_comments`의 프로필 임베드는 외래키를 지정해야 한다 (5단계에서 발견)

```
GET /event_comments?select=id,profiles(nickname)   → 300 Multiple Choices
GET /event_comments?select=id,profiles!user_id(nickname) → 200
```

`comment_reactions(comment_id, user_id)`가 `event_comments`와 `profiles` 사이의
**정션 테이블**이라, PostgREST 입장에서 두 테이블을 잇는 경로가 두 개입니다
(직접 FK `user_id`, 그리고 reactions를 통한 다대다). 어느 쪽인지 말해 줘야 합니다.

같은 이유로 `calendar_members`나 `event_participants`는 문제가 없습니다 — 정션이
하나뿐입니다. 정션이 될 수 있는 테이블을 추가하면 기존 임베드 쿼리가 깨질 수 있으니
`npm run db:smoke`가 이 두 경우를 다 확인합니다.

## 16-g. 5단계에서 뺀 것

- **댓글 반응(`comment_reactions`)** — 테이블과 정책은 있지만 화면에 넣지 않았습니다.
  이모지 선택 UI가 붙으면 댓글 영역이 커지는데, 지금은 대화가 되는지가 먼저입니다.
- **댓글 수정** — 삭제(soft delete)만 넣었습니다. 짧은 대화에서는 지우고 다시 쓰는
  편이 빠릅니다.
- **첨부 이미지** — Storage 정책은 1단계에 있지만 업로드 화면은 별도 단계입니다.

## 16-h. 알림을 큐에 넣는 일은 DB가 한다 (6단계)

`notification_outbox`를 채우는 것은 클라이언트가 아니라 **트리거**입니다(`0010`).

클라이언트가 넣게 두면 두 가지가 깨집니다.

- 일정은 저장됐는데 앱이 죽거나 네트워크가 끊기면 알림만 통째로 샙니다. 트리거로
  두면 **일정이 저장됐다는 사실과 알림이 큐에 들어갔다는 사실이 같은 트랜잭션**
  안에 있습니다.
- anon key로 아무에게나 알림을 보낼 수 있게 됩니다. `notification_outbox`에는 정책이
  하나도 없고 권한도 회수돼 있어서, 클라이언트는 큐를 읽지도 쓰지도 못합니다.

수신자는 `calendar_members`에서 **행위자 본인**과 **`muted = true`**를 뺀 나머지입니다.
음소거는 화면에서 거르는 것이 아니라 **큐에 들어가지도 않습니다.** 그래서 나중에
켜도 지난 알림은 오지 않습니다 — 화면에 그렇게 적어 뒀습니다.

`dedup_key`는 `'{사건}:{대상}:{수신자}'` 꼴이고 UNIQUE입니다. 같은 사건이 두 번
들어와도 `on conflict do nothing`이 막습니다. 수정 알림만 `updated_at`을 키에 넣어,
고칠 때마다는 새 알림이되 같은 수정이 중복되지는 않게 했습니다.

메모(`description`)만 바꾼 경우는 알리지 않습니다. 제목·시간·장소·반복이 바뀔 때만
남을 깨웁니다.

### 당시에는 없던 것 — 발송 워커

이 단계에서는 큐만 만들고 비우는 쪽은 두지 않았습니다. 이후 개발 배포 경계를 정리하며
Expo Push 발송·재시도·receipt 확인·죽은 토큰 비활성화를 Edge Function으로 추가했습니다.
현재 구조와 외부 서비스 연결 방법은 19절과 `docs/deployment.md`에 기록했습니다.

## 16-i. 리마인더는 내 것만 (6단계)

`event_reminders.user_id`가 NULL이면 캘린더 공통 리마인더지만, 화면은 **본인 것만**
다룹니다. 정책도 본인 것만 넣게 되어 있습니다. 남의 폰을 울리게 하는 설정은 만드는
사람과 받는 사람이 달라서 사고가 나기 쉽습니다.

리마인더를 제때 큐에 넣는 스캔도 워커 몫입니다. 반복 일정의 다음 회차를 알아야 하는데
그 전개는 TypeScript(`lib/recurrence.ts`)에 있고 Postgres에는 RRULE 파서가 없습니다.

## 16-j. 하루를 더할 때는 정오를 기준으로 (6단계에서 발견)

`eventDayKeys`가 자정 기준 `Date`에 `setDate(+1)`을 하고 있었습니다. **서머타임 때문에
자정이 존재하지 않는 날**(예: `America/Santiago`의 전환일)에는 그 값이 같은 날짜로
되돌아와, 같은 날짜 키가 두 번 나오고 목록이 어긋납니다.

정오를 기준으로 잡으면 ±1시간이 움직여도 날짜를 넘지 않습니다. 하루씩 밀지 않고
`new Date(y, m, d + i, 12)`로 만들어 누적 오차도 없앴습니다.

## 16-k. 활동 로그와 알림은 규칙이 다르다 (7단계)

같은 사건을 두 곳에 남기지만 **판단 기준이 다릅니다.** 그래서 트리거를 합치지 않고
따로 뒀습니다(`0010` 알림, `0011` 활동).

| | 알림 | 활동 |
|---|---|---|
| 질문 | "누구에게 알릴까" | "무슨 일이 있었나" |
| 행위자 본인 | **뺀다** | **남긴다** |
| 음소거(`muted`) | 뺀다 | 무관하다 |
| 메모만 수정 | 알리지 않는다 | 남긴다 |

한쪽 규칙을 고칠 때 다른 쪽이 딸려 오면 안 됩니다. "메모 고친 것도 알림 보내자"와
"메모 고친 건 기록도 하지 말자"는 서로 다른 결정입니다.

`summary.changed`에 무엇이 바뀌었는지 배열로 남겨, 화면이 "시간을 바꿨어요"라고
구체적으로 말할 수 있게 했습니다.

`activity_logs`는 클라이언트에게 **읽기 전용**입니다(0005가 SELECT만 줍니다).
쓰기는 전부 security definer 트리거를 통합니다.

### 겪은 것 — `text[] || 'title'`

Postgres에서 `changed := changed || 'title'`은 오른쪽을 **배열 리터럴**로 읽으려다
`22P02 malformed array literal`로 깨집니다. 일정 수정이 통째로 400이 됐습니다.
`array_append(changed, 'title')`로 바꿨습니다. INSERT 경로는 이 코드를 타지 않아
"일정 생성"만 테스트했으면 놓쳤을 버그입니다.

## 16-l. 한국어 조사를 골라 쓴다 (7단계)

"저녁 약속을(를) 추가했어요"처럼 두 형태를 함께 쓰면 읽기 나쁩니다.
`src/lib/korean.ts`가 앞 글자 받침을 보고 하나만 고릅니다.

한글 음절은 U+AC00부터 종성 28개 단위로 배열돼 있어서 `(code - 0xAC00) % 28`이 0이면
받침이 없습니다. 숫자와 영문은 **읽는 소리**로 판단합니다 — "회의 1을"(일), "회의 2를"(이),
"Excel을"(엘), "Zoo를"(오). 판단할 수 없는 글자(이모지 등)로 끝나면 받침 없는 쪽을
씁니다. 둘 중 하나는 골라야 하고 "를"이 덜 어색합니다.

## 16-m. 계정 삭제 — "지우면 무엇이 남는가"를 먼저 정했다 (8단계)

스토어 심사 필수 요건이라 앱 안에서 스스로 지울 수 있어야 합니다. 그런데 `profiles`를
그냥 지우면 **외래키 여섯 개에 막힙니다**(`calendars.owner_id`, `events.created_by`,
`event_comments.user_id`, `calendar_invites.created_by`, `memos.created_by`,
`attachments.uploaded_by` — 전부 NO ACTION).

막히는 것을 뚫는 문제가 아니라 **정책을 정하는 문제**입니다.

### 남이 함께 보는 내용은 남긴다

내가 만든 일정과 댓글은 가족의 캘린더에도 들어 있습니다. 내가 나간다고 그 사람들의
기록까지 사라지면 안 됩니다. 설계안 5.3의 "탈퇴한 구성원의 흔적은 남기고 '알 수 없는
사용자'로 표시한다"와 같은 원칙입니다. 컬럼을 nullable로 바꾸고 `on delete set null`을
걸었습니다. **화면은 이미 이 상태를 처리하고 있었습니다.**

### 소유한 캘린더는 두 갈래

- **다른 구성원이 있으면 → 가장 먼저 들어온 사람에게 넘긴다.** 남은 사람들이 쓰던
  캘린더가 통째로 사라지면 안 됩니다. "넘기고 나서 지우세요"라고 막아 세우는 쪽이
  더 정확해 보이지만, 그러면 계정을 지울 수 없는 상황이 생기고 그건 심사 요건에
  어긋납니다.
- **나 혼자면 → 통째로 지운다.** 아무도 볼 수 없는 데이터를 남길 이유가 없습니다.
  soft delete가 아니라 hard delete입니다 — "내 데이터를 지워 달라"는 요구니까요.

`delete_my_account()` 하나가 이전·삭제·탈퇴·계정 제거를 한 트랜잭션으로 처리합니다.
`account_deletion_preview()`가 누르기 전에 무엇이 어떻게 되는지 보여 줍니다.

### 지운 다음에 어디로 가나

처음엔 계정 화면으로 떨어졌습니다. 그런데 이 앱은 **가입을 앞세우지 않습니다.**
로그아웃도 "로그인 화면에 가두지 않는다"며 새 게스트 세션으로 되돌립니다.
계정 삭제도 같아야 합니다 — 지우고 나면 **앱을 처음 켠 것과 같은 상태**가 됩니다.
그래서 삭제 로직을 `AuthProvider`로 옮겨 로그아웃과 같은 자리에 뒀습니다.

## 16. 3단계에서 일부러 뺀 것

- **반복(RRULE)** — 스키마와 `rrule_until`, 예외 테이블은 1단계에 이미 있지만 전개 로직은
  4단계입니다. 지금 만드는 일정은 전부 단일 일정입니다.
- **일정별 색(`events.color`)** — 컬럼은 있지만 화면에 넣지 않았습니다. 공유 캘린더에서
  색은 "어느 캘린더인가"를 가리키는 정보라, 일정마다 색을 다르게 두면 그 뜻이 흐려집니다.
  필요해지면 그때 넣습니다.
- **참여자·리마인더·댓글** — 설계안의 별도 단계.

## 17. 세션 저장소

Supabase 세션을 `AsyncStorage`에 둡니다(Supabase의 Expo 가이드 기본값).
`expo-secure-store`는 저장 가능한 값의 크기가 제한될 수 있어 세션 JSON을 그대로 담기
어렵습니다. 토큰을 OS 보안 저장소에 두려면 청크 분할 어댑터가 필요합니다 — 네이티브
모듈은 첫 iOS 빌드에 포함하되 어댑터 연결은 **하드닝 항목으로 남겨둡니다.**

## 18. 홈은 캘린더에만 집중하고, 확정 색 토큰을 적용한다

홈 상단의 닉네임과 계정 아바타, 하단의 계정 전환 배너를 제거했습니다. 계정 관리는 하단
설정 탭에서 계속 접근할 수 있으므로 홈에 같은 진입점을 반복할 필요가 없고, 월간 격자와
선택한 날의 일정에 화면을 더 집중시키는 쪽을 택했습니다.

`docs/design-decisions.md` 5장의 살구 light/dark 토큰과 12색 라벨 팔레트를 코드에
반영했습니다. 캘린더 색은 light 배경을 DB의 안정적인 값으로 저장하고, 렌더링할 때 현재
밝기에 맞는 배경·글자 쌍으로 바꿉니다. 팔레트의 명도 교대 순서가 접근성 규칙이므로 배열
순서는 고정입니다.

기존 8색 데이터는 `20260727000100_calendar_palette.sql`에서 대응하는 새 슬롯으로 한 번만
옮깁니다. 임의로 지정한 색은 건드리지 않습니다. 앱바·탭바 색은 `chrome` 토큰으로 분리해
향후 테마를 늘려도 화면 코드가 브랜드 색을 직접 알지 않게 했습니다.

## 19. 로컬 구현과 개발 배포의 경계를 코드로 고정한다

로컬 Supabase와 Expo 웹만 뜨는 상태는 기능 확인에는 충분하지만 실제 기기·공유 링크·원격
알림을 검증할 수는 없습니다. 개발·미리보기·운영 앱을 한 바이너리로 섞지 않도록
`app.config.ts`와 `eas.json`에서 앱 이름, 스킴, iOS 번들 ID를 환경별로 나눴습니다.
`npm run deploy:check`는 로컬 Supabase URL, 예시 ID, 누락된 EAS project ID를 배포 전에
실패시킵니다.

알림은 `notification_outbox`를 클라이언트가 직접 비우지 않습니다.
`claim_notification_outbox()`가 service role만 사용할 수 있는 짧은 lease로 행을 가져오고,
Edge Function이 기기별 delivery를 기록합니다. 일시 오류는 지수형 지연으로 다시 시도하고,
Expo receipt를 확인해 `DeviceNotRegistered` 토큰은 비활성화합니다. 리마인더 전개는 앱과
같은 `event-time.ts`·`recurrence.ts`를 사용해 반복 일정과 타임존 규칙을 두 벌로 만들지
않았습니다.

초대 링크는 `EXPO_PUBLIC_UNIVERSAL_LINK_BASE_URL`이 있으면 HTTPS 링크를 만들고, 앱 설정은
iOS associated domain을 선언합니다. 알림을 눌렀을 때는 임의 URL을
열지 않고 UUID가 검증된 일정·캘린더 내부 경로만 이동합니다.

코드로 대신할 수 없는 외부 경계는 네 가지입니다. Supabase Cloud 프로젝트, Expo/EAS
프로젝트, 앱 링크를 제공할 HTTPS 도메인, Apple 서명 정보입니다. 이 값과 실제
배포 순서는 `docs/deployment.md` 한 곳에 모았습니다.

## 20. 첫 iOS 빌드는 OTA로 바꿀 수 없는 경계를 넉넉히 잡는다

Android를 배포하지 않기로 했으므로 EAS profile, 앱 식별자, 유니버설 링크 생성기를 iOS
기준으로 줄였습니다. 첫 iOS 바이너리에는 EAS Update, 기기 캘린더, 사진·파일 선택,
파일 처리, iOS 공유 시트, 보안 저장소, 앱 버전 조회, Sentry 네이티브 SDK를 포함합니다.
이후 이 모듈을 사용하는 화면과 로직은 OTA로 붙일 수 있습니다.

`runtimeVersion`은 앱 버전을 기준으로 하고 preview/production 채널을 분리합니다. 네이티브
모듈·권한·entitlement·Expo SDK가 달라지면 `version`을 올리고 다시 빌드하며, 화면·쿼리·
상태 로직은 같은 runtime 안에서 OTA로 보냅니다.

권한은 기능 이름만 보고 모두 미리 요청하지 않습니다. 사진 보관함 읽기와 기기 캘린더
읽기처럼 예정된 기능에 필요한 문구만 바이너리에 선언했고 카메라·마이크·Face ID는
제외했습니다. 실제 권한 팝업도 해당 기능을 누르는 시점에만 띄웁니다.

`expo-sharing` config plugin은 외부 앱에서 TimeFlower로 보내는 Share Extension을 추가해
별도 target과 app group까지 관리하게 됩니다. 현재 필요한 것은 TimeFlower에서 iOS 공유
시트를 여는 동작이므로 모듈만 autolink하고 extension은 만들지 않았습니다.

Sentry DSN이 없으면 SDK는 꺼져 있고, 연결 뒤에는 앱 환경과 EAS Update ID를 오류에
붙입니다. DSN은 공개 설정이지만 소스맵 업로드 토큰은 EAS secret으로만 관리합니다.
로컬 웹 미리보기는 iOS 네이티브 오류 수집 범위가 아니므로 `observability.web.ts`의
no-op 경계를 사용해 React Native용 Sentry SDK를 웹 번들에 포함하지 않습니다.

## 21. 살구는 기본 브랜드, 쪽빛·먹빛은 사용자 테마로 제공한다

시안에서 준비한 세 방향을 모두 실제 테마로 내기로 확정했습니다. 살구는 앱 아이콘·스플래시와
첫 실행의 기본값이고, 사용자는 설정에서 쪽빛 또는 먹빛으로 바꿀 수 있습니다. 선택은 계정에
동기화하지 않고 `AsyncStorage`에 기기별로 저장합니다. 함께 쓰는 캘린더라도 사람마다 앱의
옷은 다르게 고를 수 있어야 하기 때문입니다.

색 구조는 `ThemePalettes[theme][scheme]`으로 잡아 테마 3개와 시스템 라이트/다크 2개를
조합합니다. 화면은 계속 `useTheme()`만 사용하므로 새 테마를 알아야 할 코드가 설정 화면
밖으로 번지지 않습니다. 캘린더 라벨 팔레트는 데이터 부호이므로 사용자 테마를 따라 바꾸지
않습니다.

## 22. 설정 탭을 더보기 허브와 기기별 표시 설정으로 나눈다

설정 탭에 계정·테마·알림을 길게 나열하던 구조를 `더보기` 허브로 바꿨습니다. 모바일에서
자주 쓰는 메모, 일정 검색, 설정, 알림, 활동, 캘린더 관리를 3열 바로가기로 먼저 보여 주고,
계정과 현재 캘린더 표시 설정은 그 아래 카드에 요약합니다. 별도 상세 설정 화면에는 실제
동작이 연결된 항목만 둡니다. 아직 서비스에 없는 프리미엄·실험실·고객 지원 항목은 다른
앱의 레이아웃을 채우기 위해 임의로 만들지 않았습니다.

한 주의 시작, ISO 주 번호, 음력 날짜, 시간대, 토요일 색상은 `calendar-preference`에
기기별로 저장합니다. 한 주의 시작을 바꾸면 격자만 회전하는 것이 아니라 월간 일정 조회
범위도 같은 6주 범위로 바뀝니다. 음력은 `Intl`의 단기 달력을 지원하는 환경에서만
표시하고, 지원하지 않는 엔진에서는 잘못된 변환값을 대신 보여 주지 않습니다.

사진의 메모·검색 진입점은 장식용 버튼이 아니라 기존 `memos` 테이블의 작성·완료·삭제와
접근 가능한 일정 제목 검색으로 구현했습니다. 언어 행은 현재 제공되는 한국어를 명확히
표시하되, 화면 문자열 전체가 아직 다국어 리소스로 분리되지 않았으므로 동작하지 않는 언어
선택기를 만들지 않았습니다. 다국어 전환은 문자열 카탈로그와 스토어 현지화를 함께 묶는
후속 배포 작업으로 남깁니다.

## 23. 날짜 상세는 시간축 목록과 작은 추가 액션을 사용한다

월간 캘린더에서 같은 날짜를 다시 누르면 열리는 상세 모달은 별도의 대형 CTA를 두지 않습니다.
날짜와 음력 날짜를 왼쪽에, 작은 원형 `+` 버튼을 오른쪽에 배치해 일정 목록이 첫 화면의 중심이
되도록 했습니다. 일정은 시작·종료 시각, 캘린더 색 막대, 제목 순서의 시간축 형태로 표시하며,
행을 누르면 기존 일정 상세로 이동합니다. 일정이 없는 날에도 `+` 버튼은 같은 자리를 유지해
추가 위치가 흔들리지 않습니다.

## 24. 날짜 스티커는 캘린더가 소유하고 구성원이 함께 본다

날짜 상세의 반짝이 버튼을 누르면 스티커보다 대상 캘린더를 먼저 고릅니다. 월간 화면이 여러
캘린더를 겹쳐 보여 주기 때문에, 장식도 어느 공유 공간의 데이터인지 먼저 정해야 구성원과
권한이 명확해집니다. 선택한 다음에는 오리지널 일러스트 6종을 세로형 타일로 미리 보고,
누르면 날짜 상단의 가로 배너로 즉시 적용합니다. 같은 날짜에 여러 캘린더 스티커가 있으면
방금 바꾼 캘린더를 우선 보여 주고 캘린더 이름과 나머지 개수를 함께 표시합니다.

`calendar_stickers`는 `(calendar_id, sticker_date)`마다 한 행만 가지며, 구성원만 읽기·
추가·변경·삭제할 수 있습니다. 클라이언트 UPDATE 권한은 `sticker_key`만 열어 날짜나
캘린더 식별자를 바꾸는 우회를 막았습니다. 스티커는 일정이나 활동 기록이 아니라 가벼운
꾸미기 데이터라 알림과 활동 로그를 만들지 않습니다.

일러스트는 기존 서비스 캐릭터를 복제하지 않은 TimeFlower 전용 동물 장면이며
`assets/stickers/`의 512px JPEG 정적 자산입니다. 네이티브 모듈 추가 없이 `expo-image`로
표시하므로 현재 runtime에서 OTA로 전달할 수 있습니다.

## 25. 월간 캘린더는 세로로 움직이지 않고 좌우 스와이프로 달을 넘긴다

메인 화면에서 날짜 상세 영역을 제거한 뒤에는 월간 캘린더 아래로 이어지는 핵심 콘텐츠가
없으므로 화면 전체를 세로 스크롤하지 않습니다. 월 제목·필터·6주 격자를 한 화면에 고정하고,
격자를 왼쪽으로 스와이프하면 다음 달, 오른쪽으로 스와이프하면 이전 달로 전환합니다.
전환 시에는 손가락을 놓은 뒤 달만 갑자기 바꾸지 않습니다. 이전·현재·다음 달 격자를
가로로 이어 붙인 3페이지 트랙을 사용해 현재 달과 옆 달이 손가락 이동을 그대로 따라오고,
놓았을 때 임계값을 넘겼으면 옆 달로, 넘기지 못했으면 현재 달로 부드럽게 안착합니다.
수동 `PanResponder` 임계값 애니메이션 대신 React Native의 가로 `ScrollView`에
`pagingEnabled`와 한 달 너비의 스냅 간격을 적용합니다. 따라서 iOS의 기본 페이지 감속과
안착 동작을 그대로 사용하고, 한 번에 한 달만 넘기며, 전환 뒤에는 3페이지를 가운데로
재배치해 계속 이어서 넘길 수 있습니다.
날짜를 누르는 동작과 충돌하지 않도록 수평 이동량이 수직 이동량보다 뚜렷할 때만 스와이프로
판정합니다. 이전·다음 달 화살표는 화면에서 제거하고, 보조 기술에는 월간 격자의
증가·감소 접근성 액션으로 같은 이동 경로를 제공합니다.

## 26. 캘린더 대표 사진과 날짜 스티커를 월간 화면에 직접 표시한다

캘린더 설정에서 정사각형 대표 사진을 추가·교체·삭제할 수 있습니다. 사진 원본은 공개 URL이
아니라 기존 `calendar-media` 비공개 버킷의
`{calendar_id}/covers/{uuid}.{ext}` 경로에 저장하고, 구성원에게만 1시간짜리 서명 URL을
발급합니다. 메인 화면에서는 캘린더 필터의 색 점 자리를 24px 썸네일로 바꾸되, 사진이 없는
캘린더는 기존 색 점을 그대로 사용합니다. 설정을 함께 편집할 수 있는 구성원은 이전 업로더가
달라도 교체된 커버 파일만 정리할 수 있고, 일정 첨부파일 삭제 권한은 넓히지 않습니다.

날짜 상세에서 붙인 스티커는 이제 월간 격자의 해당 날짜 왼쪽 아래에도 표시합니다. 상세
상단과 선택 화면은 장면 전체가 있는 원본 이미지를 유지하고, 작은 월간 칸은 배경을 제거한
42px 캐릭터 PNG를 사용해 사각 사진이 아니라 실제 스티커처럼 보이게 합니다. 화면에 그려지는
6주 범위를 한 번에 조회하고, 사용자가 숨긴 캘린더의 스티커는 일정과 마찬가지로 숨깁니다.
한 날짜에 여러 캘린더의 스티커가 있으면 첫 이미지를 보여 주고 `+N` 배지로 나머지 개수를
표시합니다.

## 27. 월 제목은 연도·월 선택기의 진입점으로 사용한다

월간 화면의 이전·다음 화살표는 두지 않고 좌우 스와이프만 빠른 월 이동에 사용합니다.
멀리 떨어진 달로 이동할 때 스와이프를 반복하지 않도록 상단의 `YYYY년 M월` 제목 자체를
버튼으로 만들었습니다. 제목을 누르면 1900~2100년 목록과 12개월 격자가 함께 열리고,
월을 고르는 즉시 해당 월의 첫날로 이동합니다. 월 제목 옆의 아래 방향 표시는 선택기가
열린다는 뜻이며 이전·다음 달 이동 버튼이 아닙니다.

외부 캘린더를 연결하지 않은 상태의 조회 훅은 `pending`이지만 실제 네트워크 요청은
`idle`일 수 있습니다. 날짜 상세 화면은 이를 무한 로딩으로 오해하지 않도록, 외부 일정에
대해서는 첫 조회가 실제 진행 중일 때만 참인 `isLoading`을 사용합니다.

## 28. 월간 격자는 남은 화면을 채우고 포커스 상태 자체가 상세 진입 기준이다

기기 높이에서 고정 숫자를 빼 날짜 셀 높이를 계산하면 상단 안전 영역·탭 바·폰 크기에 따라
사용하지 못하는 빈 공간이 생깁니다. 메인 캘린더 카드를 남은 영역의 `flex: 1`로 만들고,
요일 아래 6개 주가 그 높이를 똑같이 나눠 쓰도록 바꿨습니다. 좌우 여백도 기존 디자인
토큰의 최소 간격까지 줄여 월간 격자가 화면을 더 넓게 사용합니다.

캘린더별 필터 줄은 콘텐츠 계산에 따라 줄어들지 않도록 44px 프레임으로 고정합니다.
캘린더 조회가 실패해 칩 데이터가 없더라도 `필터 다시 불러오기`와 `필터 관리` 진입점은
남겨, 필터 영역 전체가 사라진 것처럼 보이지 않게 합니다.

날짜 상세 진입은 별도의 “마지막으로 누른 날짜” 기록이 아니라 현재 포커스 날짜만 봅니다.
포커스되지 않은 날짜를 누르면 포커스하고, 이미 포커스된 날짜를 누르면 즉시 상세 모달을
엽니다. 따라서 상세 모달을 내린 뒤에도 포커스가 유지되고 같은 날짜를 한 번만 눌러 다시
열 수 있습니다.

## 29. 월간 화면에서 종일 일정과 시간 지정 일정을 형태로 구분한다

월간 격자의 일정 막대가 모두 같은 배경을 가지면 종일 일정과 특정 시각의 약속을 제목만으로
구분해야 합니다. 종일 일정은 기존처럼 캘린더 색으로 채운 배경 막대를 사용하고, 시간 지정
일정은 배경을 없앤 뒤 왼쪽에 2px 캘린더 색 세로선만 표시합니다. 색각에만 의존하지 않고
면과 선이라는 형태 차이로 일정 종류를 알아볼 수 있습니다. 정렬은 기존처럼 종일 일정이
먼저, 시간 지정 일정이 그다음입니다.

캘린더 카드의 좌우 바깥 여백과 월간 격자 자체의 좌우 패딩도 제거했습니다. 상단 제목과
필터는 읽기·터치 여백을 유지하지만, 날짜 7열은 콘텐츠 최대 너비 전체를 사용합니다.

## 30. 화면 스타일과 글자 설정은 기기별 접근성 설정으로 둔다

라이트·다크 화면은 기본적으로 운영체제 설정을 따르되, 사용자가 이 앱에서만 라이트 또는
다크로 고정할 수 있습니다. 색상 테마(살구·쪽빛·먹빛)와 화면 명암은 서로 독립된 축이며,
두 선택 모두 계정이나 공유 캘린더 데이터가 아닌 이 기기의 AsyncStorage에 저장합니다.

글자 크기는 기존 타이포그래피 토큰 값을 바꾸지 않고 `작게 0.92배`, `보통 1배`,
`크게 1.1배`, `매우 크게 1.2배`를 마지막에 적용합니다. React Native의 시스템 글자
확대는 끄지 않았으므로 iOS 손쉬운 사용의 텍스트 크기와 앱 안의 배율이 함께 반영됩니다.
글꼴은 시스템 기본, 나눔고딕, 나눔명조 중 고를 수 있고 한글 400·700 굵기 파일만 앱에
포함합니다. 사용자 글꼴 파일을 불러오지 못한 경우에는 스플래시 화면에 머물지 않고 시스템
글꼴로 계속 실행합니다.

## 31. 일정 편집 모달은 한 화면짜리 핵심 폼과 보조 시트로 나눈다

일정 추가·수정 화면은 긴 세로 폼과 하단 저장 버튼 대신 네이티브 모달 헤더의 왼쪽에 닫기,
오른쪽에 저장을 둡니다. 본문은 제목, 캘린더, 종일 여부, 시작·종료, 반복, 장소, 메모를
44~64px 높이의 행으로 압축하고 세로 `ScrollView`를 사용하지 않습니다. 날짜와 시각은
각각 별도 행으로 쌓지 않고 한 행 오른쪽에 나란히 둡니다. 새 일정 화면의 첨부 초안도
세로 파일 목록 대신 가로 칩으로 표시합니다.

수정 화면의 첨부·참여자·미리 알림·댓글은 저장과 독립적으로 즉시 반영되는 기능이라 핵심
폼 아래의 짧은 도구 막대에서 별도 page sheet로 엽니다. 보조 시트 내부는 내용이 늘어날 수
있으므로 스크롤을 허용하지만, 일정 편집 메인 시트는 항상 한 화면에 유지합니다. 반복 일정의
적용 범위와 삭제는 데이터 변경 범위를 결정하므로 메인 폼에 남깁니다.

## 32. 등록된 일정은 보기와 수정을 분리

- 캘린더에서 기존 일정을 열면 입력 폼 대신 읽기 전용 상세 화면을 먼저 보여 준다.
- 상단에는 뒤로가기, 작성자 프로필, 더보기 메뉴를 두고 더보기의 `일정 수정`을 통해서만 편집 화면으로 이동한다.
- 상세 화면은 제목과 시작·종료 시각을 가장 크게 보여 주고, 알림·캘린더·장소·메모와 등록 이력을 아래에 배치한다.
- 기존 첨부 파일·참여자·알림·댓글 기능은 하단의 작은 도구 모음에서 시트로 연다. 긴 부가 정보 때문에 핵심 일정 정보가 밀리지 않게 하기 위함이다.

## 33. 캘린더 설정 변경도 활동 로그에 남긴다

캘린더 이름·색상·대표 사진이 바뀌면 `CALENDAR_UPDATED` 활동을 DB 트리거가 기록합니다.
클라이언트가 로그를 직접 쓰지 않으므로 이전 앱 버전이나 직접 API 요청으로 수정해도 같은
규칙이 적용됩니다. `summary.changed`에는 `name`, `color`, `cover`만 저장하며 같은 값을
다시 저장하거나 `updated_at`만 바뀐 경우는 기록하지 않습니다. 소유권 이전과 구성원 변경은
기존 활동 규칙과 의미가 다르므로 이 로그에 섞지 않습니다.

## 34. 소셜 로그인은 계정 전환과 게스트 연결을 다른 흐름으로 취급한다

`계정 만들기`에서 Google·Apple을 선택하면 새 사용자로 로그인하지 않고 현재 익명 사용자에
identity를 연결합니다. 따라서 `auth.users.id`와 게스트 때 만든 캘린더·일정이 유지됩니다.
iOS Apple 연결도 브라우저 OAuth로 우회하지 않고 네이티브 ID token linking을 사용합니다.
Apple 요청에는 매번 암호학적 난수 nonce와 state를 만들고, 돌아온 state 및 Supabase가
검증한 nonce를 모두 확인합니다.

`로그인`은 이미 존재하는 다른 사용자로 세션을 교체하는 흐름입니다. 전환 전에 현재
사용자의 이 기기 푸시 토큰을 DB에서 떼고, 로그인 취소·실패로 같은 사용자에게 남으면
복구합니다. 성공하면 사용자 id 변경을 `AuthProvider`가 감지해 React Query 캐시 전체를
비우므로 이전 계정의 캘린더가 새 계정 화면에 잠시 남지 않습니다. Google 웹 인증은 저장된
쿠키가 있어도 `prompt=select_account`로 계정을 직접 고르게 합니다.

OAuth callback은 시작 시 만든 redirect 주소와 scheme·host·path가 정확히 일치할 때만
일회용 code를 교환합니다. 소셜 가입 때 입력한 닉네임은 기존 익명 프로필에 반영합니다.
소셜 로그인 자체는 `openid`, 이메일, 기본 프로필만 사용하며 Google Calendar나 iOS
캘린더 권한은 별도의 외부 캘린더 기능에서만 요청합니다.

## 35. 홈의 캘린더 생성 빈 상태 카드는 두지 않는다

홈은 사용자의 캘린더 보유 여부와 무관하게 월간 캘린더가 화면의 남은 높이를 전부
사용합니다. 캘린더가 없을 때도 `함께 볼 캘린더를 만들어요` 안내 카드와
`캘린더 만들기` 버튼을 홈에 추가하지 않습니다. 캘린더 생성과 관리는 상단의
`필터 관리` 화면에서 진입합니다. 이 결정으로 앱 시작 직후 캘린더 목록을 불러오는
짧은 동안 빈 상태 카드가 나타났다 사라지며 월간 캘린더의 높이가 바뀌는 현상도
없어집니다.

## 36. 서비스명을 TimeFlower로 바꾸되 배포 식별자는 유지한다

사용자에게 노출되는 서비스명과 앱 표시 이름, 권한 안내, 설정 문구, 개인정보 처리방침,
스토어 제출 자료를 `TimeFlower`로 통일합니다. 새 아이콘과 스플래시는 전달받을 시안이
확정된 뒤 한 번의 네이티브 빌드에 함께 반영합니다.

이미 TestFlight에 올라간 앱과 설치된 사용자의 연속성을 위해 Bundle ID
`com.hiorio.timeline`, EAS project ID와 slug, `timeline://` OAuth scheme,
`timeline-*` AsyncStorage 키는 바꾸지 않습니다. Bundle ID 변경은 App Store에서
별도 앱을 만들고, scheme이나 저장 키 변경은 기존 빌드의 로그인과 기기 설정을
끊기 때문입니다.

## 37. 초기 출시에서는 소셜 로그인을 제공하지 않는다

Google·Apple 로그인은 Google Calendar나 iOS 기기 캘린더를 읽는 기능과 별개이며,
외부 캘린더를 직접 연동하지 않는 초기 출시 범위에는 필수가 아닙니다. 게스트 시작과
이메일 계정만으로 공유 캘린더의 데이터 유지·다른 기기 로그인 요구를 충족합니다.

계정 화면에서 Google·Apple 버튼과 공급자 상태 조회를 제거했습니다. 구현 파일은 향후
재검토를 위해 남기되 `SOCIAL_AUTH_ENABLED=false`를 `AuthProvider` 내부에서도 검사해,
Supabase 공급자가 실수로 활성화되더라도 소셜 로그인이나 identity 연결을 호출할 수 없게
막습니다. 다시 제공할 때는 이 값을 켜는 것만으로 끝내지 않고 공급자 설정, 계정 충돌,
사용자 간 데이터 격리 테스트를 다시 통과해야 합니다.

계정 안내 문구도 가입을 필수 절차처럼 보이게 하지 않습니다. 기본 설명은
`가입 없이도 앱을 사용할 수 있어요`로 시작하고, 계정의 목적을 재설치·기기 변경 뒤
데이터를 이어 쓰는 선택 사항으로 설명합니다. 기존 계정 로그인 화면에서는 위험 경고 대신
`로그인은 기존 계정을 불러옵니다`라는 정보 안내를 사용하되, 현재 게스트 데이터를
보존하려면 계정 만들기를 선택해야 한다는 사실은 숨기지 않습니다.

## 38. TimeFlower 꽃 아이콘은 원본의 손그림 느낌을 유지한다

전달받은 꽃 시안을 최종 원본으로 채택했습니다. 자동 보정 시안은 꽃잎 균형은 좋아졌지만
원본에 없던 그라데이션과 지나치게 정형화된 형태가 생겨 사용하지 않았습니다. 원본 PNG는
`assets/brand/timeflower-icon-source.png`에 보관하고, 생성 스크립트가 iOS용 1024px
아이콘과 스플래시·파비콘을 리샘플링합니다. 스플래시 배경도 원본 모서리색
`#EBE5DC`로 맞춥니다.

## 39. 첫 출시 대상은 iPhone으로 한정하고 스플래시 이미지는 투명 배경을 쓴다

초기 App Store 배포에서는 `ios.supportsTablet`을 끄고 iPhone만 공식 지원합니다. iPad 전용
레이아웃과 멀티태스킹 동작을 충분히 검증한 뒤 별도 네이티브 빌드에서 다시 지원합니다.
이 값은 네이티브 앱의 기기 지원 범위를 바꾸므로 OTA가 아니라 새 App Store 빌드가 필요합니다.

스플래시 화면은 불투명한 정사각형 꽃 이미지와 네이티브 배경 사이의 미세한 색상 경계가
보이지 않도록 꽃 바깥을 투명 처리합니다. 꽃의 형태와 색은 원본을 유지하고 네이티브
스플래시 배경 `#EBE5DC`가 그대로 비치게 합니다. `npm run icons`를 다시 실행해도 같은
방식으로 투명 스플래시 자산을 생성합니다.

운영 EAS Submit은 App Store Connect의 TimeFlower 앱 ID `6795333546`을 명시합니다. 과거
개발 앱의 ID `6795329202`를 사용하면 같은 Apple 계정의 API 키로도 운영 앱을 찾지 못해
업로드 전에 실패하므로, 운영 제출 프로필에서 개발 앱 ID를 재사용하지 않습니다.

## 40. 일별 상세는 날짜 페이저로 탐색하고 수정·삭제 동작을 바로 실행한다

일별 상세 화면은 이전·현재·다음 날짜 세 페이지를 가로로 배치하고, 스와이프가 끝나면
가운데 페이지를 새 현재 날짜로 재사용합니다. 월간 화면과 같은 방식이라 날짜가 화면에
붙어 이동하고 연속으로 넘길 수 있습니다. 페이지마다 해당 월의 일정과 외부 캘린더,
스티커를 조회하되 같은 월 데이터는 React Query 캐시를 공유합니다.

일정 상세의 `…`는 선택지가 사실상 수정 하나뿐이던 시스템 액션시트나 팝오버를 거치지 않고
현재 회차의 일정 수정 화면을 바로 엽니다. 반복 일정이면 `occ`를 그대로 넘겨 수정 범위와
표시 값이 사용자가 누른 회차에 맞게 유지됩니다.

일별 일정 행을 왼쪽으로 밀면 오른쪽에 휴지통 버튼이 나타납니다. 버튼을 눌러 삭제 확인을
마치면 단일 일정은 기존 규칙대로 soft delete하고, 반복 일정은 현재 날짜의 회차만 취소
예외로 남깁니다. 같은 방향을 쓰는 날짜 페이저가 행 제스처를 빼앗지 않도록 행을 미는 동안
페이저를 잠깐 멈추며, 읽기 전용인 외부 기기 캘린더 일정에는 삭제 동작을 노출하지 않습니다.

## 41. 스티커 카탈로그를 6종에서 12종으로 확장한다

기존 장면형 6종에 `생일 파티`, `꽃다발 선물`, `바닷가 휴가`, `달빛 단잠`, `쿠키 굽기`,
`오늘도 운동`을 추가합니다. 새 6종은 작은 월간 칸에서도 형태가 흐려지지 않도록 투명 배경의
단일 캐릭터 컷아웃을 유지하고, 선택 화면과 일별 배너에는 같은 캐릭터가 들어간 별도의 512px
장면 JPG를 사용합니다. 월간 칸에서는 기존 원칙대로 별도의 카드 배경 없이 투명 컷아웃만
표시합니다. 상세용 배경과 월간용 컷아웃을 카탈로그에서 분리해 한 화면의 요구가 다른 화면의
가독성을 바꾸지 않게 합니다.

스티커 키는 클라이언트 카탈로그뿐 아니라 `calendar_stickers.sticker_key` 체크 제약에도 같은
12종을 허용합니다. 따라서 새 스티커를 포함한 앱을 배포하기 전에 해당 DB 마이그레이션을 먼저
적용해야 합니다.

## 42. iOS 위젯은 조회 범위와 빠른 작성 대상을 분리한다

Expo SDK 57의 `expo-widgets`로 iPhone 바탕화면용 소형·중형·대형 캘린더와 빠른 메모
위젯, 잠금화면용 원형·직사각형·인라인 위젯을 제공합니다. 위젯 구성 API는 설치 때 정한
정적 선택지만 지원하므로 캘린더 목록을 iOS 위젯 편집기에 복제하지 않고, 앱의
`설정 > 바탕화면·잠금화면 위젯`에서 기기별로 한 번 설정합니다.

표시 범위는 `앱과 같게`, `모두`, `직접 선택` 중 하나이며 여러 캘린더를 합쳐 보여줄 수
있습니다. 반면 빠른 일정·메모의 저장 대상은 정확히 한 캘린더만 지정합니다. 캘린더가 여러
개인데 대상을 지정하지 않았다면 위젯이 임의로 첫 캘린더를 고르지 않고 빠른 작성 화면에서
사용자에게 선택받습니다. 이 구분은 개인 내용을 공유 캘린더에 잘못 저장하는 사고를 막습니다.

WidgetKit은 텍스트 입력 UI를 제공하지 않으므로 위젯의 추가 버튼은 딥링크로 앱의 최소 입력
화면을 엽니다. 일정은 제목·캘린더·시간 종류만, 메모는 내용·캘린더만 받으며 기존
`events`·`memos` mutation을 그대로 사용합니다. 위젯 확장에 Supabase 세션이나 anon key를
복사하지 않고, 앱이 RLS를 거쳐 읽은 표시용 스냅샷만 공유 저장소에 전달합니다. 사용자 ID가
바뀌면 새 조회가 끝나기 전에 스냅샷을 먼저 비워 이전 사용자의 일정이 남지 않게 합니다.

현재 Expo 57의 Android 위젯 구현은 이름만 출력하는 실험적 렌더러이므로 Android에는
확장을 생성하지 않습니다. 같은 설정 저장소와 딥링크 화면은 공용으로 두되, 실제 Android
위젯은 공식 렌더러가 캘린더 UI와 상호작용을 지원한 뒤 별도 네이티브 빌드로 추가합니다.
이번 변경은 기존 테이블과 정책을 재사용하므로 DB 마이그레이션은 없습니다.

## 43. 월간 홈은 사용자별 최소 스냅샷을 먼저 보여 주고 현재 달부터 갱신한다

앱을 완전히 다시 켜면 React Query의 메모리 캐시가 비어 있어 월간 격자는 먼저 보이지만
일정 제목과 스티커는 네트워크 응답 뒤에 나타났습니다. 전체 쿼리 캐시를 영속화하면 상세
메모까지 암호화되지 않은 AsyncStorage에 남고, 사용자 id가 없는 쿼리 키 하나를 빠뜨렸을 때
이전 사용자의 데이터가 노출될 위험도 커집니다.

따라서 홈 화면이 실제로 그리는 일정 id·제목·색·종일 여부와 스티커만 최대 3개월치 저장합니다.
스냅샷에는 사용자 id와 `월 + 주 시작 설정` 키를 함께 넣고 현재 세션과 둘 다 일치할 때만
사용합니다. 다른 사용자의 값이나 손상된 값은 즉시 폐기하며 로그인·로그아웃·계정 삭제
경로에서도 최선 노력으로 지웁니다. 화면은 이 값을 먼저 그리고 Supabase 최신 응답이 오면
교체하므로, 삭제되거나 수정된 일정도 네트워크 연결 뒤에는 그대로 남지 않습니다.

첫 진입의 네트워크 경쟁도 줄입니다. 현재 달 일정이 끝난 뒤에 이전·다음 달 일정과 스티커를
요청하고, 화면에 보이지 않는 iOS 위젯의 다음 달 조회도 현재 달 조회 뒤로 미룹니다. 이후
사용자가 달을 넘길 때는 준비된 인접 달 캐시를 그대로 사용합니다. 기존 테이블·RLS·GRANT는
바꾸지 않으므로 DB 마이그레이션은 없습니다.

## 44. iOS 종일 일정은 UTC 순간을 기기 날짜로 복원한다

Expo Calendar의 iOS 모듈은 EventKit 날짜를 UTC ISO 문자열로 넘깁니다. 한국 시간의
8월 21일 자정이 `8월 20일 15:00Z`로 표현될 때 문자열 앞의 날짜만 사용하면 종일 일정이
하루 전으로 이동합니다. 시간대가 포함된 값은 해당 순간을 기기 타임존의 벽시계 날짜로
복원하고, 날짜만 넘어온 값은 타임존 변환 없이 그대로 유지합니다. EventKit의 배타 종료일은
기존 앱 규칙인 포함 종료일로 변환하며, 날짜 연산은 서머타임의 영향을 받지 않게 UTC에서
수행합니다. 외부 일정은 계속 읽기 전용이며 Supabase 스키마 변경은 없습니다.

## 45. 위젯 도입 전 바이너리에는 위젯 코드를 로드하지 않는다

EAS Update 채널에는 같은 runtime의 여러 빌드가 연결될 수 있습니다. 위젯 네이티브 모듈을
추가하기 전 바이너리가 위젯을 정적으로 import하면 OTA 적용 직후 앱 시작 단계에서 모듈을
찾지 못합니다. 따라서 `ExpoWidgets` 네이티브 모듈이 실제로 등록된 iOS 바이너리에서만
위젯 동기화 모듈을 지연 로드하고 위젯 설정을 노출합니다. 위젯 포함 새 바이너리는 앱 버전을
올려 runtime을 분리하며, 이전 바이너리는 나머지 JS 화면 개선을 계속 OTA로 받을 수 있습니다.

## 46. Google·Apple 로그인은 게스트 연결과 기존 계정 전환을 분리해 다시 제공한다

초기 출시에서 숨겼던 Google·Apple 로그인을 계정 화면에 다시 노출합니다. `계정 만들기`에서
선택하면 현재 익명 사용자의 identity에 연결해 사용자 id와 기존 캘린더·일정을 유지하고,
`로그인`에서 선택하면 기존 소셜 계정의 사용자로 세션을 전환합니다. 이미 다른 사용자에게
연결된 identity를 게스트에 연결하려 한 경우에는 새 계정을 만들지 않고 로그인 탭으로 안내합니다.

iOS Google 로그인은 네이티브 SDK의 ID token 흐름을 사용하고 웹에서는 Supabase PKCE OAuth와
`prompt=select_account`를 유지합니다. Apple은 iOS 네이티브 Authentication Services에서 매
요청마다 nonce와 state를 만들어 검증합니다. Apple의 정식 시스템 버튼은 실제 기기에서 API가
제공될 때만 렌더합니다. 계정 화면은 GoTrue 공개 settings를 읽어 운영 서버에서 활성화된
공급자만 사용 가능하게 하고, 로그인에는 이메일·기본 프로필만 요청합니다. 기기 캘린더 접근은
기존 읽기 전용 외부 캘린더 기능과 계속 별개입니다.

## 47. 일정 행 스와이프는 같은 터치의 상세 열기를 취소한다

일별 목록의 일정 행은 `Pressable`과 삭제용 `ReanimatedSwipeable`이 겹쳐 있어, 일부 기기에서
왼쪽으로 민 손가락을 놓을 때 행의 `onPress`까지 실행될 수 있습니다. 스와이프 시작 콜백에서
해당 행의 상세 열기를 차단하고, 열림·닫힘 애니메이션이 정착한 직후에만 다시 허용합니다.
차단 중 전달된 press는 소비만 하고 라우팅하지 않으므로 삭제 버튼을 드러내는 동작이 일정
상세 화면으로 이어지지 않습니다. 탭만 한 경우에는 기존처럼 즉시 상세를 엽니다.

## 48. 일정 상세는 수정 화면에서 돌아오면 표시 데이터를 다시 확인한다

일정 상세 위에 수정 화면을 모달로 열면 상세 컴포넌트는 언마운트되지 않고 뒤에 남습니다.
따라서 수정 후 돌아와도 최초 마운트 기준 쿼리가 그대로 보일 수 있습니다. 상세 화면이 다시
포커스를 받을 때 일정 마스터, 반복 회차 예외, 캘린더 정보를 무효화해 최신 값을 다시
받습니다. 최초 진입은 각 쿼리가 이미 요청하므로 중복 호출하지 않습니다.

캘린더 이름과 색은 일정 범위·검색·상세 쿼리에 조인되어 캐시됩니다. 캘린더 수정 성공 시
캘린더 쿼리뿐 아니라 일정 쿼리도 함께 무효화해 월간 화면과 상세 화면에 이전 이름이나 색이
남지 않게 합니다. 기존 테이블과 정책만 사용하므로 DB 마이그레이션은 없습니다.

## 49. 기존 계정 로그인에는 게스트 데이터 이관 선택을 둔다

`계정 만들기`는 게스트 identity에 이메일이나 소셜 identity를 연결하므로 기존 사용자 id와
데이터가 자동으로 유지됩니다. 반면 이미 존재하는 계정으로 로그인하면 사용자 id가 바뀌므로,
로그인 직전에 이 기기에서 만든 캘린더를 `가져오기`, `가져오지 않기`, `로그인 취소` 중에서
명시적으로 선택하게 합니다. 가져오지 않아도 원본을 삭제하지 않으며 그 계정에서만 보이지
않는다는 점을 함께 알립니다.

가져오기에 동의하면 게스트 세션이 15분짜리 일회용 토큰을 만들고, 인증 전환 뒤 정식 계정이
그 토큰을 청구합니다. 서버는 캘린더 소유권·멤버십과 일정, 댓글, 메모, 스티커, 첨부파일,
참여자·리마인더·반응의 사용자 참조를 한 트랜잭션으로 합칩니다. 토큰은 데이터를 직접 읽는
권한이 아니며 게스트는 청구할 수 없습니다. 성공 응답이 유실돼도 같은 대상 계정의 재청구만
멱등 허용하고, 다른 계정의 재사용은 막습니다. 앱이 중간에 종료되면 로컬에 잠시 보관한 토큰을
다음 시작 때 다시 청구합니다. 푸시 토큰은 계정 사이에 넘기지 않고 새 계정에서 다시 등록합니다.

## 50. iOS Google 로그인은 브라우저 대신 네이티브 ID token 흐름을 사용한다

iOS의 Google 로그인은 `@react-native-google-signin/google-signin`으로 계정 선택과 동의를
받고, 반환된 ID token을 Supabase `signInWithIdToken()` 또는 `linkIdentity()`에 직접
전달합니다. 인증 중간에 Supabase 호스트를 브라우저로 열지 않으므로 사용자는 TimeFlower 앱과
Google 시스템 화면만 보게 됩니다. 로그인 전에는 SDK의 로컬 선택 상태를 지워 매번 사용할
Google 계정을 명시적으로 고르게 합니다.

Google iOS SDK는 Supabase가 대조할 요청 nonce를 앱에 노출하지 않으므로 공급자의
`Skip nonce checks`를 켭니다. 이는 nonce 기반 재전송 방어를 사용할 수 없다는 절충이며,
허용 audience는 등록한 웹·iOS client ID로 제한하고 토큰 검증과 세션 발급은 계속 Supabase가
수행합니다.

계정 만들기에서는 현재 게스트에 identity를 연결해 사용자 id와 기존 캘린더를 유지하고,
기존 계정 로그인에서는 49절의 데이터 이관 선택을 그대로 거칩니다. Google Calendar scope는
요청하지 않으며 이메일과 기본 프로필만 사용합니다. 웹은 네이티브 모듈을 로드하지 않고 기존
Supabase PKCE 흐름을 유지합니다.

이 모듈이 없는 1.2.0 바이너리에 새 JS가 OTA로 전달되면 시작 단계에서 실패할 수 있으므로 앱
버전과 runtime을 1.3.0으로 올려 분리합니다. iOS OAuth 클라이언트 ID는 공개 EAS 환경 변수로
주입하고 config plugin이 역방향 URL scheme을 생성합니다. 이 설정을 바꾸면 새 네이티브 빌드가
필요합니다.

## 51. 새 일정은 선택한 날짜의 현재 시각으로 시작한다

일정 추가 화면은 모든 날짜를 오전 9시로 초기화하지 않고, 사용자가 화면을 연 시점의
시·분을 선택한 날짜에 적용합니다. 종료는 한 시간 뒤로 두며 피커에 표시되지 않는 초와
밀리초는 버립니다. 다른 일정을 복사해 추가할 때는 복사한 일정의 원래 시각을 유지합니다.

위젯·바로가기에서 여는 빠른 일정은 짧은 입력에 맞춰 다음 30분 경계를 쓰는 기존 규칙을
유지합니다. 일반 일정 추가와 빠른 일정은 진입 목적이 달라 같은 반올림 규칙을 공유하지
않습니다.

## 52. 전용 시간 다이얼은 실제 일정과 분리해 A안을 먼저 시험한다

iOS 시스템 시각 선택기를 바로 교체하지 않고 `시간 선택기 실험실` 화면에서 A안을 먼저
시험합니다. 처음에는 오전·오후, 시, 10분 단위(`00·10·20·30·40·50`) 휠만 보여 주고,
10분 휠을 움직이면 그 오른쪽에 선택 구간의 정확한 분 10개가 자동으로 나타납니다.

실험 화면의 결과는 로컬 화면 상태에만 반영하고 일정이나 DB에는 저장하지 않습니다. 진입점은
개발 빌드 또는 `EXPO_PUBLIC_TIME_PICKER_LAB_ENABLED=true`인 테스트 빌드에서만 더보기에
노출합니다. 실제 iPhone에서 레이아웃 이동, 선택 속도, VoiceOver와 큰 글자를 확인해 승인된
뒤에만 일정 추가·수정 화면으로 연결합니다.

## 53. 전용 시간 다이얼은 A·B·C 세 안을 같은 빌드에서 비교한다

A안은 기준안으로 남겨 `30`을 고르면 실제 분 `30~39`가 자동으로 펼쳐집니다. B안은
10분 단위 옆에 1분 자리 `0~9`를 항상 보여 주고 두 값을 더해 실제 분을 만듭니다. 예를 들어
왼쪽 `30`과 오른쪽 `7`은 `37분`입니다. C안도 같은 `0~9` 조합을 쓰지만 처음에는 오른쪽
휠을 숨기고, 10분 단위를 고른 뒤 손을 떼고 같은 휠을 0.6초 길게 누르면 펼칩니다.

세 안 모두 기존 오전·오후, 시, 10분 휠의 위치를 고정하고 오른쪽 클리핑 영역만 넓힙니다.
따라서 세부 휠이 나타날 때 기존 휠이 함께 밀리지 않고, 새 휠이 10분 휠에서 이어져 나온다는
관계가 보입니다. B·C안에는 현재 조합식도 함께 표시합니다.

Expo 57이 노출하는 SwiftUI 롱프레스는 휠 스크롤과 하나의 연속 제스처로 결합되지 않습니다.
휠을 돌린 손가락을 그대로 둔 채 기다리면 이동 거리 때문에 롱프레스가 취소될 수 있으므로,
이번 실험의 동작 계약은 `선택 → 손 떼기 → 다시 길게 누르기`입니다. 끊김 없는
`드래그 → 대기`가 꼭 필요하다는 결론이 나면 제스처를 직접 조정하는 iOS 네이티브 모듈로
다음 실험을 만듭니다. VoiceOver 사용자는 숨은 휠을 직접 열 수 있는 보조 버튼도 제공합니다.

이번 세 안은 계속 실험실 로컬 상태에만 결과를 반영하며 일정·DB에는 쓰지 않습니다. 테스트
빌드 노출 플래그와 실제 일정 화면에 적용하기 전 승인 절차도 52절과 같습니다.
